# Zag Store signed metadata v2 — production rollout gates

Status: **staged only**. The live Stable/Beta/Nightly updater continues to use
the existing v1 channel manifests. Do not publish or activate v2 yet.

## Trust-key handling

1. Generate the Ed25519 production signing key **offline**, under operator
   control. Never commit or upload its private half, seed, password or backup.
2. Export only the public PEM key. Use
   `scripts/inspect-zag-v2-public-key.py --public-key <public.pem> --key-id <id>`
   to display its raw base64 bytes and SHA-256 fingerprint.
3. Verify the fingerprint through an independent operator-controlled channel
   before committing the public key to a dedicated immutable trust-root source.
4. Embed approved public keys in the app, keyed by stable key IDs. The trust
   dictionary must not be downloaded from the same update channel it verifies.
5. Plan overlapping trust roots for key rotation; never silently replace or
   remove an existing root without a reviewed transition.

## Required work before activation

- Replace the current Swift ASCII-only Foundation serialization check with a
  **tested RFC 8785 JCS implementation**, or constrain the Python publisher
  and Swift verifier to the same explicitly specified canonical subset.
  The Python publisher currently uses `jcs`; Swift currently rejects non-ASCII.
  Unicode release notes must not be published until this is resolved.
- Harden v2 envelope parsing: reject duplicate or unknown envelope keys and
  unexpected types; enforce an envelope size limit and a payload size limit.
- Test actual Python-signed manifests in the full Swift signature → semantic
  validation → Keychain rollback pipeline, including tampering, expiry, channel
  mismatch, Unicode and key rotation.
- Test missing Keychain entitlements, access failures, app reinstall, and
  recovery from corrupt records on a real signed iPhone build.
- Decide how to handle two app processes accessing the same rollback account;
  actor isolation only serializes callers inside one process.
- Document trust-root recovery, emergency revocation and key-compromise response.
- Publish canonical unsigned-by-user IPA artifacts and v2 manifests only after
  checksums, versions, bundle IDs and HTTPS origins have been verified.
- Keep v1 checks active until a signed v2-enabled client has been distributed
  and its migration behavior validated; **never silently fall back from a
  rejected v2 manifest to unauthenticated v1** once v2 is enforced.
- Establish a channel-by-channel cutover and rollback plan, including signed
  metadata sequence continuity and expiration/clock-skew handling.

## Current compatibility

The existing v1 update URLs and in-place local signing behavior remain
unchanged. The staged `ZagUpdateVerifiedPipeline` is not invoked by the live
coordinator. No production public key has been committed and no private key
has been generated by these scripts.
